# Playroom 架構整理計畫

建立日期：2026-10-11

本計畫針對自營平台：由自己或可信任開發者提供遊戲，持續增加遊戲、玩家與版本，維持簡單部署。目的是在規模擴大前穩定接入契約、資料相容性與模組邊界。

本輪 01–07 已完成，完成範圍、驗證證據與未處理限制以各文件的核取方塊及交付記錄為準。各項「規劃時現況」與階段交付紀錄保留當時的基準、測試數量及限制；目前進度以本文件「最新進度」為準。未勾選的設計不能視為現行 API 已提供。沒有壓力測量證據時不能宣稱容量提升。

## 建議執行順序

1. **先定義跨遊戲契約：**完成 01 的版本與能力設計、02 的存檔讀寫及回退規則、06 的錯誤格式。先記錄相容策略，再實作，避免三項各自發明一套協定。
2. **建立必要的內部基礎：**完成 04 中與本輪有關的模組拆分，以及 05 的 migration runner 與 schema 版本集中管理。單純搬移與行為變更分開提交。
3. **落實接入與資料保障：**實作 01、02、06；涉及新增資料表時使用 05 建立的方式。
4. **改善後台資料流：**在 04 的功能邊界內完成 03，移除對全量 overview 的依賴；沿用 06 的衝突與錯誤處理。
5. **完善維護與恢復：**完成 07，補齊 05 的升級／還原測試與本輪文件。

01、02 的契約設計應先做；05 中必要的 migration 基礎需早於新增存檔快照或安裝日誌資料表。各文件中的編號是識別碼，不代表嚴格執行順序。

## 實作與交付原則

- 保留單體服務、SQLite、單一 app 實例及可信任開發者模型。
- 保留平台與遊戲不同來源、版本不可覆寫、人工預覽確認、逐次權限檢查、Origin／CSRF 保護。
- 不在本輪引入微服務、Redis、WebSocket、多節點部署或任意使用者上傳。
- 優先沿用既有測試與工具；每次提交集中處理一項可驗收行為，避免一次改完所有子系統。
- 每個子任務完成後勾選文件中的核取方塊，記錄驗證結果與未處理限制。
- 影響遊戲開發、Manifest、SDK、打包、Release 或匯入／預覽／發布流程時，**同一次修改**更新 `templates/game-agent-template.md` 及相應規格。
- 範本「開始前讀取線上規格」連結必須保持追蹤平台 `main`；工具產物可版本化，不得因此把文件連結固定為 commit SHA。
- 本資料夾同時保存未來設計与已完成驗證；只有已勾選且有證據的項目代表本輪交付，未完成 API、欄位或保障不能宣稱已提供。

## 共用驗證門檻

- 程式變更通過 `npm run typecheck`、`npm run build` 與相關單元／整合測試。
- 認證、發布、播放器、後台資料流變更執行相關 Playwright 測試；整合交付時執行完整既有 CI。
- 資料庫與檔案安裝變更必須包含舊資料升級、備份還原或中斷恢復測試。
- 外部接入變更必須驗證既有遊戲及舊 SDK，不能只測最新範例。
- 以測試資料建立規模基準，記錄資料量、回應大小、查詢次數與時間；沒有測量前不宣稱容量提升倍數。
